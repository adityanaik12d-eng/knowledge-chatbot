A prior session's notes claimed this had already been fixed and the old 384-dim rows wiped, but live inspection today showed the column was still `384` — meaning that earlier fix never actually persisted (or was undone by something else). Verified fixed by successfully uploading a PDF, DOCX, and image afterward. **Lesson:** don't trust a past log entry claiming a schema fix is in place — verify the live schema directly before investigating anything else, especially when a failure spans multiple unrelated file types at once (a strong signal the bug is in a shared step, not per-file-type parsing).

## Known Pitfalls (learned the hard way — avoid repeating)

- Don't let an AI agent freely rearchitect an already-working piece without being asked; verify library imports exist before using them; confirm large pastes/file writes actually completed in full; prefer PowerShell heredoc over interactive Notepad; deleting a `profiles` row doesn't delete the `auth.users` account; Supabase free-tier email sending can silently rate-limit during heavy test signups; re-creating a test account resets `department` to `'unassigned'`.
- Full-file regenerations by Claude Code (even when only asked to make a small edit) can silently drop previously-applied fixes, AND can introduce brand-new, unrelated syntax errors (a missing arrow-function token, a missing closing brace) that have nothing to do with the requested change — always re-verify specific fixes are present, AND run the file through an actual parser, after any Claude Code session.
- A "VERIFIED" claim from an AI code-editing tool is not fully trustworthy on its own if the verification only checks *presence* of a pattern, not *correctness* of its placement or overall file validity.
- Third-party blog posts about LLM-provider free-tier limits can be outdated or wrong — always confirm against the provider's own official docs before switching models based on a blog claim.
- A silent/hanging LLM API call is a different failure mode from an explicit error response, and needs different diagnosis via logs.
- When asked to "revert everything to how it was," be explicit about what specifically gets reverted and what side effects that has.
- Time-boxing a CPU-bound operation by wall-clock duration does not guarantee it stays under a platform's actual CPU-time budget — always retest with the actual failing input before declaring a fix resolved.
- `supabase.functions.fetch(...)` is not a real method on the Supabase JS client (the correct method is `.functions.invoke()`) — this exact mistake has appeared more than once across regenerated files.
- When switching a frontend call to `supabase.functions.invoke()`, the target Edge Function's CORS `Access-Control-Allow-Headers` must include `x-client-info` (added automatically by `.invoke()`) or every call fails preflight with a generic, misleading error.
- `profiles.last_sign_in_at` does not exist — that data only lives in `auth.users`, read via `auth.admin.listUsers()` inside a service-role-backed Edge Function.
- **New:** Never trust a Memory.md/log entry claiming a database schema change (e.g. a vector dimension fix) is "done" without re-checking the live schema directly — a past fix can fail to persist, or get silently undone, without anything in the code history showing it. When a failure spans multiple unrelated file types or code paths at once, that's a strong signal the bug is in a shared step (e.g. a DB write, an auth check, an embedding call) rather than in any one of the specific paths that appear to be failing.
