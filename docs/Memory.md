## Known Pitfalls (learned the hard way — avoid repeating)

- (carried forward from before, still true) Don't let an AI agent freely rearchitect an already-working piece without being asked; verify library imports exist before using them; confirm large pastes/file writes actually completed in full; prefer PowerShell heredoc over interactive Notepad; large PDFs and scanned/image PDFs have known extraction limits; deleting a `profiles` row doesn't delete the `auth.users` account; Supabase free-tier email sending can silently rate-limit during heavy test signups; re-creating a test account resets `department` to `'unassigned'`.
- **New this round:** Full-file regenerations by Claude Code (even when only asked to make a small edit) can silently drop previously-applied fixes if the AI decides to "rewrite" more than instructed — always re-verify specific fixes are present (grep/read the actual file, not a memory of what was asked) after any Claude Code session, especially after a large or multi-part prompt.
- **New this round:** A confirmed "VERIFIED" claim from Claude Code is not fully trustworthy on its own if the verification checklist only checks *presence* of a pattern, not *correctness* of its placement (e.g. `ref: messagesContainerRef` existed inside the file both times it broke — checking "does this string exist" isn't the same as checking "is this a valid React ref prop, not a bogus style key").
- **New this round:** Third-party blog posts about LLM-provider free-tier limits (TPM/RPM, which models are active) can be outdated or wrong — always confirm against the provider's own official docs before switching models based on a blog claim (this cost several wasted iterations with Groq's `gemma2-9b-it`, which was already fully decommissioned).
- **New this round:** A silent/hanging LLM API call (no error, no response, just timeout) is a different failure mode from an explicit error response, and needs different diagnosis — check edge function logs for whether the outbound request was even attempted and whether *any* response (success or error) came back, rather than assuming a config/key problem.
- **New this round:** When a user asks to "revert everything to how it was," be explicit about what specifically gets reverted and what side effects that has (e.g. reverting a chunking fix also silently un-fixes the CPU-timeout bug it was solving) — don't let "revert" quietly erase unrelated, still-valid fixes without flagging it.
